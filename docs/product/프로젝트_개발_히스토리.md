# 지투라이브 포트폴리오 케이스 스터디

## 1. 한 줄 소개

지투라이브는 국내 정규장 이후에도 움직이는 해외 주식 연동 파생상품을 이용해 한국·미국 주식의 24시간 참고 추정가를 제공하고, 실제 거래상품과 추정값의 차이를 투명하게 설명하는 멀티자산 시장 대시보드다.

프로젝트는 지민재가 기획, 공개 데이터 API 통합, UI/UX, 테스트, GitFlow, CI/CD와 배포까지 제품 개발 전 과정을 학습하고 증명하기 위한 개인 프로젝트다.

## 2. 왜 이 프로젝트를 기획했는가

국내 증권 앱은 정확한 실제 시세와 거래 기능을 제공하지만 정규장이 끝나면 한국 주식의 대표 가격은 멈춘다. 반면 해외 시장의 한국 주식 연동 파생상품은 야간과 휴장 시간에도 움직이며 다음 국내 시장에 대한 기대를 반영한다.

처음에는 증권사 Open API로 실제 시세와 개인 보유종목을 표시하는 대시보드로 시작했다. 개발 과정에서 다음 문제가 드러났다.

- 개인 API 자격증명과 고정 IP는 공개 다중 사용자 서비스에 맞지 않았다.
- 5초 폴링이 중복되면서 429 요청 제한 오류가 발생했다.
- 개인 보유종목은 공개 배포판에 노출할 수 없었다.
- 실제 시세의 재배포와 광고형 서비스에는 별도의 데이터 권리가 필요했다.
- 주말·휴장 중에는 실제 주식 가격 자체가 존재하지 않는다.

이 문제를 계기로 제품의 질문을 바꿨다.

> 실제 주식 시세를 복제하는 대신, 공개 데이터만으로 24시간 시장 기대를 얼마나 정직하고 유용하게 표현할 수 있는가?

## 3. 기획 변화의 역사

### 0.1: 실제 시세와 개인 자산 대시보드

- Toss Invest API로 한국·미국 주식과 개인 보유종목을 표시했다.
- 브라우저에서 5초마다 dashboard API를 조회했다.
- 429 오류와 공개 배포 환경의 고정 IP·재배포 문제가 확인됐다.

### 0.3: cache와 공개 화면 정리

- 같은 cache miss의 동시 요청을 하나로 합쳤다.
- 공급자별 TTL, 429 `Retry-After`, 회로 차단을 추가했다.
- 공개 배포판에서 개인 보유자산을 제거했다.
- GitFlow, 한국어 중심 Conventional Commit, CHANGELOG와 기술 문서를 정착시켰다.

### 0.4: 24시간 파생 추정가로 전환

- 공개 배포판에서 Toss 의존성을 제거했다.
- Hyperliquid·Binance 파생상품과 Bithumb 합성환율을 사용했다.
- 실제 주식 시세가 아니라 `24시간 추정가`임을 UI에 표시했다.
- 공급자, 기준 시각, 비교 기준과 환산 근거를 노출했다.

### 0.4 세션 개편: 세션 인식과 검증 가능한 추정가

- 프리·KRX 정규·NXT 애프터·야간을 구분한다.
- 한국 주식 원화 추정 candle과 상세 OHLC를 제공한다.
- 거래량은 `추종상품 거래량`으로 의미를 분리한다.
- 공급자 24시간 등락률과 국내 종가 기준 등락률을 혼합하지 않는다.
- 동일 시각 기준 오차를 수집해 종목별 신뢰도를 평가한다.

## 4. 핵심 알고리즘

### 현재 원화 추정가

```text
estimatedKrw(t)
= derivativePrice(t) × bithumbKrwUsdt(t)
```

- Hyperliquid 한국 주식 연동 상품은 `markPx`를 사용한다.
- Binance 토큰화 주식 무기한선물은 `lastPrice`를 사용한다.
- Bithumb `KRW-USDT`는 은행 고시환율이 아니라 거래상품 기반 합성환율이다.
- 입력 하나라도 없거나 오래됐으면 가격을 만들지 않는다.

### 기준점 보정 후보

```text
calibration
= verifiedDomesticClose
/ (derivativeAtClose × fxAtClose)

calibratedEstimate
= derivativeNow × fxNow × calibration
```

보정은 무조건 적용하지 않는다. 실제 종가의 사용 권리와 기준 시각이 검증되고, 백테스트에서 지속적인 편향을 줄인다는 근거가 있을 때만 적용한다.

### 원화 candle

현재 구현은 사용자가 선택한 주기의 파생상품 candle과 같은 timestamp의 환율 candle을 결합한다. 같은 timestamp가 없으면 해당 파생 candle보다 과거이면서 주기별 허용 시간 안에 있는 가장 가까운 환율만 사용하고, 미래 환율로 과거 값을 채우지 않는다.

```text
openKrw  = derivativeOpen × fxOpen
highKrw  = max(derivative high·low × fx high·low 네 조합)
lowKrw   = min(같은 네 조합)
closeKrw = derivativeClose × fxClose
```

두 시장의 고가·저가 발생 시점은 candle 내부에서 다를 수 있으므로 high·low는 실제 국내 체결값이 아니라 보수적인 원화 추정 범위다. 1분 원시봉을 먼저 환산한 뒤 상위 봉으로 재집계하는 방식은 이 오차를 더 줄이기 위한 후속 정밀화 단계로 남겨두었다.

### 오차율

```text
APE(t)
= abs(estimate(t) - actual(t)) / actual(t)
```

20분 지연 실제값은 20분 전에 저장한 추정가와 비교한다. 현재 추정가와 지연값을 비교하면 시장 움직임과 모델 오차가 섞이기 때문이다.

## 5. KRX에는 가깝고 NXT에는 차이가 나는 이유

Hyperliquid의 삼성전자 상품은 KRX `005930` 보통주 1주를 참조하고 원화 가격을 달러로 환산한다. 따라서 정규장에는 KRX 가격과 가까워지는 것이 자연스럽다.

NXT는 KRX와 별도의 주문장과 체결을 가진 대체거래소다. 같은 종목이어도 참여 주문, 유동성, 마지막 체결 시각이 달라 가격이 순간적으로 다를 수 있다. NXT 공식 공개 화면은 20분 지연이므로 현재 추정가와 그대로 비교하면 시간 차이까지 포함된다.

제품은 다음 원칙을 사용한다.

- KRX 정규장에는 KRX 추종을 대표 기준으로 삼는다.
- NXT 프리·애프터에는 NXT를 오차 평가 기준으로 삼는다.
- KRX와 NXT 실제값을 보유하지 않으면 실시간 시세라고 표시하지 않는다.
- NXT와 다르다는 이유만으로 KRX 추종 가격을 강제로 보정하지 않는다.

## 6. 중요한 기술적 의사결정

### 서버 cache로 방문자 수와 외부 호출 수 분리

브라우저 1,000명이 접속해도 공급자 API를 1,000번 호출하지 않는다. 서버가 공급자별 snapshot을 한 번 갱신하고 모든 방문자에게 cache된 결과를 제공한다.

### 공급자별 장애 격리

Hyperliquid 장애가 Bithumb 코인과 Binance 자산까지 막지 않도록 결과를 자산군별로 합성한다. stale 값에는 마지막 정상 시각을 표시하고 한계를 넘으면 숨긴다.

### 실제값과 추정값을 타입으로 구분

`actual-product`, `derived-estimate`, `unavailable`을 데이터 계약에서 구분한다. UI 문구만으로 구분하면 새로운 화면에서 실수로 실제값처럼 표시할 가능성이 있기 때문이다.

### 미지원은 숫자보다 낫다

검증되지 않은 심볼, 계약 단위 또는 환율에는 예시 가격이나 임의 fallback을 사용하지 않는다. 금융 화면에서는 빈 상태가 잘못된 확신보다 안전하다.

### 증권사 API 제거

증권사 수가 많다는 사실과 공개 재배포 권리는 별개의 문제다. 개인 거래용 API를 여러 개 연결하는 대신 공개 서비스에 적합한 데이터 권리와 확장성을 우선했다.

## 7. 해결한 주요 문제

### Toss API 429

원인:

- 여러 화면과 방문자가 같은 5초 주기로 계좌·시세 API를 반복 호출했다.

해결:

- 데이터별 TTL cache
- 같은 요청의 in-flight 병합
- `Retry-After` 기반 재시도
- 공급자별 회로 차단
- 숨은 브라우저 탭 polling 중단

### 실제값처럼 보이는 고정 예시 가격

원인:

- 공급자 연결 전에도 샘플 숫자가 표시돼 사용자가 실시간 데이터로 오인했다.

해결:

- loading, stale, unavailable 상태를 분리했다.
- 공급자와 기준 시각을 함께 표시했다.

### 한국 주식 차트와 OHLC 미제공

원인:

- 파생 candle은 USD·USDT, 화면 가격은 KRW이므로 같은 의미를 보장할 수 없었다.
- 과거 모든 candle에 현재 환율을 곱하면 차트가 왜곡된다.

해결:

- 파생 candle과 시점별 환율 candle을 시간 정렬해 원화로 변환한다.
- Bithumb의 `timestamp`는 봉 시작이 아니라 마지막 체결 시각이므로 `candle_date_time_utc`를 우선해 Hyperliquid·Binance bucket과 정렬한다.
- 변환 근거가 없으면 차트를 숨기는 기존 안전 원칙은 유지한다.
- 상세 거래량을 `추종상품 거래량`으로 표시하고 실제 KRX·NXT 거래량이 아님을 안내한다.

### 휴장일을 평일로 오인하는 문제

원인:

- 단순 요일 계산만 사용하면 공휴일·노동절·연말 휴장일을 정규장으로 표시할 수 있다.

해결:

- KST 기준 세션 판별과 2026년 확인 휴장일을 분리된 순수 함수로 구현했다.
- 달력이 등록되지 않은 연도는 정상 영업으로 추측하지 않고 휴장 상태로 처리한다.
- 새 연도 운영 전 공식 KRX 휴장 규칙과 공휴일 변경을 검토해 정적 목록을 갱신하도록 한계를 문서화했다.

### 차트의 날짜 반복과 가격 정보 분산

문제:

- 분봉의 모든 시간 눈금에 날짜와 시간을 함께 표시해 같은 날짜가 반복되고 실제 장중 흐름을 빠르게 읽기 어려웠다.
- 종목명과 현재가·등락률이 화면 양쪽으로 분리되어 종목을 선택한 뒤 핵심 시세를 찾는 시선 이동이 컸다.
- 시가·고가·저가·종가가 차트 밖 카드에만 있어 특정 candle을 확인할 때 차트와 숫자를 번갈아 봐야 했다.

해결:

- 차트 라이브러리가 제공하는 `year`, `month`, `day`, `time` 눈금 유형을 구분해 날짜 경계에는 `9월 2일`, 같은 날에는 `10:15`처럼 표시한다.
- 종목명 바로 아래 현재가와 등락률을 배치하고 심볼·세션·가격 성격을 다음 정보 계층으로 내렸다.
- 차트 내부에 최신 또는 crosshair candle의 OHLC를 표시하고 불러온 구간의 고가·저가를 캔들 위치에 표시한다.
- 거래량은 공급자 데이터의 성격을 명시해 차트 하단에 표시한다.

### 보조지표·선 그리기 시도와 보류 결정

원인:

- 차트가 화면에 보여줄 candle만 요청해 MA 120의 첫 119개 구간에는 계산 입력이 없었다.
- MA 180은 공급자 응답이 180개 이하이면 값이 없거나 한 점만 생겨 선으로 표시할 수 없었다.
- Hyperliquid `xyz:SKHX`를 2017년부터 요청해도 실제 상장 이후인 2026년 데이터만 반환했다.

검토 과정:

- 프로토타입에서는 화면 범위와 지표 계산 범위를 분리하고 최대 240개 warm-up candle을 추가해 MA 120·180을 계산했다.
- 추세선·수평선·수직선을 시장 좌표로 저장하는 브라우저 전용 SVG overlay도 검증했다.
- 공급자가 반환하지 않은 2017년 이전·상장 이전 candle은 보간하거나 생성하지 않는다.

최종 결정:

- 계산 가능 여부와 투자 분석 의미는 다르다. 현재 차트는 KRX 실제 전체 이력이 아니라 공급자 상장 이후의 해외 파생상품과 합성환율 기반 추정 이력이다.
- 이 데이터에 그린 이동평균과 추세선은 실제 국내 주식의 장기 지지·저항 또는 증권사 지표처럼 오인될 수 있다.
- 0.4.0 공개 범위에서는 보조지표 설정, 선 그리기, 관련 warm-up 추가 조회와 브라우저 저장 코드를 제거한다.
- 캔들, 거래량, OHLC, 고가·저가, 날짜·시간축과 봉 단위 전환은 공급자 범위를 확인하는 기능으로 유지한다.

2017년 이후 실제 한국 주식 장기 차트는 공개 웹사이트 재배포와 광고형 서비스 이용이 허용되는 별도 공급자를 확보한 뒤 데이터 종류와 경계 시각을 분리해 추가한다. 현재 파생 추정 candle과 과거 KRX 실제값을 하나의 실제 시세처럼 조용히 연결하지 않는다.

### Supabase를 Community backend로 선택한 이유

문제:

- 혼자 개발하는 MVP에서 게시글·댓글 database, 사용자별 소유권, 접근 제어와 운영 환경을 각각 직접 구축하면 Community 자체보다 기반 작업의 비중이 커진다.
- 로그인 화면은 없애고 싶지만, browser UUID만으로는 작성자 소유권을 신뢰할 수 없다.
- Oracle 배포 application과 database를 한 서버에 강하게 묶으면 장애·백업·PC 이전과 추후 확장 부담이 커진다.

검토한 대안:

- Oracle에 PostgreSQL과 인증을 직접 운영하면 제어 범위는 넓지만, 초기부터 patch·backup·복구·보안 운영을 모두 혼자 책임져야 한다.
- Firebase는 빠른 개발이 가능하지만 현재 설계가 관계형 schema, SQL migration과 row 단위 정책을 중심으로 되어 있어 PostgreSQL 기반이 더 자연스럽다.
- 인증 전문 서비스는 OIDC·SSO·조직·복잡한 RBAC가 필요할 때 강점이 있지만, 익명 게시판 MVP의 현재 요구보다 범위와 운영 요소가 크다.

선택:

- Supabase의 관리형 PostgreSQL, anonymous Auth와 RLS를 조합해 database·인증·권한 경계를 하나의 검증 가능한 schema와 migration으로 관리한다.
- 공개 browser는 anonymous session만 만들고, 모든 write는 Vinext API가 JWT·Turnstile·rate limit을 검증한 뒤 수행한다. Supabase를 선택했다는 이유로 table direct write를 허용하지 않는다.
- Community data는 시장 데이터 공급 계층과 분리한다. Oracle은 application/API 배포를, Supabase는 Community Auth/Postgres를 담당해 한 공급자에 전체 서비스를 묶지 않는다.
- Free plan은 비용 없이 제품 가설을 검증하는 시작점으로만 사용한다. 요금 수치와 quota는 바뀔 수 있으므로 문서에 고정된 장기 보장값으로 간주하지 않는다.

선택 이유와 한계:

- 개인 프로젝트에서 빠른 구현, 표준 PostgreSQL, Git에 남는 migration, anonymous Auth와 RLS의 조합이 현재 요구에 가장 잘 맞았다.
- 오픈소스·PostgreSQL 기반은 이전 선택지를 넓혀 주지만 vendor lock-in이 사라지는 것은 아니다. Auth session, Realtime, Storage와 운영 API에 깊게 의존할수록 이전 비용이 커진다.
- Logto의 비교 글은 빠른 MVP와 초기 비용 장점을 정리하는 참고자료로 사용했다. 다만 인증 제품을 판매하는 회사의 관점이므로 Supabase의 RBAC·custom claim 능력이 없다는 주장은 그대로 채택하지 않았고, 공식 Supabase 문서에서 SQL·Auth Hook 기반 구현 가능성을 별도로 확인했다.
- 현재 제품에는 OIDC provider, enterprise SSO, 조직·다중 tenant 권한이 필요하지 않다. 해당 요구가 생기면 Supabase Auth를 억지로 확장하지 않고 인증 전문 서비스 분리 여부를 다시 검토한다.
- Free plan의 자동 backup 부재, database·egress·MAU·Realtime connection quota, 익명 계정 abuse와 운영 책임은 남는다. 정기 dump·복구 검증과 사용량 관측 없이는 production 준비가 끝난 것으로 보지 않는다.

재검토 조건:

- Free/유료 quota에 반복적으로 근접하거나 비용이 자체 운영·다른 managed Postgres보다 불리해질 때
- 복잡한 조직·역할, OIDC provider, enterprise SSO 또는 여러 서비스 간 통합 인증이 필요해질 때
- backup RPO/RTO, 가용성, connection 수와 moderation 처리량이 현재 plan으로 충족되지 않을 때
- 이 경우 database는 표준 PostgreSQL migration을 기준으로 이전 가능성을 검증하고, Auth·cache·compute를 독립적으로 교체하는 hybrid 구조를 우선 검토한다.

### 로그인 화면 없는 커뮤니티의 소유권과 abuse 방지

문제:

- 브라우저 UUID만 사용하면 저장소를 지우거나 다른 브라우저를 열어 작성·신고 제한을 쉽게 우회할 수 있다.
- 실명·전화번호 회원가입을 도입하면 MVP 범위와 개인정보 처리 부담이 크게 늘어난다.
- Supabase anonymous user도 database에서는 `authenticated` role을 사용하므로 role 이름만 보고 공개 write를 허용하면 일반 계정과 익명 계정 경계가 사라진다.

선택:

- email·phone 입력 없이 Supabase anonymous Auth가 발급한 JWT와 `is_anonymous` 값을 server에서 검증한다.
- 모든 write는 Vinext API route만 수행하고 browser role의 table write와 보안 RPC 실행 권한은 revoke한다.
- Turnstile token은 server에서 3초 timeout으로 검증하며 빈 값, 2,048자 초과, 공급자 오류와 `success !== true`를 모두 거부한다.
- 신뢰된 client IP는 `${UTC 날짜}:${정규화 IP}`에 HMAC-SHA-256을 적용한 64자리 daily abuse key로 즉시 변환하고 원본 IP는 application DB에 저장하지 않는다.
- 닉네임도 같은 secret을 `nickname:${actorId}` namespace로 분리해 만들며 UUID 일부를 화면에 노출하지 않는다.

결과와 한계:

- 같은 사용자는 같은 날 안정적으로 제한되지만 abuse key는 UTC 날짜가 바뀌면 회전한다.
- 여러 사용자가 같은 네트워크를 쓰는 경우를 고려해 일반 신고는 서로 다른 actor 10명과 abuse key 10개 조건을 모두 만족해야 숨긴다.
- 브라우저 데이터를 삭제하면 익명 계정의 기존 작성물 삭제 권한을 복구할 수 없다. UI에서 첫 작성 전에 이 한계를 알리고, 권리침해 삭제는 별도 운영 절차로 처리한다.
- HMAC·Turnstile은 abuse를 줄이는 계층이며 법적 본인 확인이나 완전한 중복 방지를 의미하지 않는다.

### 공개 Community read API의 정보 경계

문제:

- Database row를 그대로 JSON으로 반환하면 `author_id`, 신고 상태와 향후 추가되는 내부 column이 의도하지 않게 공개될 수 있다.
- `created_at`만 사용하는 cursor는 같은 시각에 생성된 글이 중복되거나 누락될 수 있다.
- 신고로 숨김 처리된 콘텐츠가 cache나 service role 조회에서 다시 노출되면 moderation 정책이 무력화된다.

선택:

- Repository query는 `select('*')` 없이 필요한 column을 명시하고 database row를 내부 record로 변환한다.
- Read service는 visible 상태를 다시 검사한 뒤 작성자 UUID와 내부 상태를 제거한 public DTO만 만든다.
- Pagination은 `(created_at, id)` 두 값을 불투명한 base64url cursor로 전달해 동일 timestamp에서도 안정적으로 다음 페이지를 찾는다.
- 상세·댓글에서 유효한 anonymous actor가 확인된 경우에만 UUID 비교 결과인 `canDelete` boolean을 추가한다.
- 개인화 여부와 즉시 숨김 상태가 공유 cache에 남지 않도록 모든 Community 응답은 `Cache-Control: no-store`를 사용한다.
- Release gate 전에는 feature flag를 false로 유지하고 route가 Supabase 연결 전에 404를 반환한다.

한계:

- Server read는 ownership 계산을 위해 내부 작성자 ID를 읽지만 API 경계 밖으로 반환하지 않는다.
- Cursor는 순서를 안정화하는 식별자이며 접근 권한을 부여하는 token이 아니다. 변조되거나 잘못된 cursor는 400으로 거부한다.
- 초기 MVP는 search와 인기순 정렬 없이 newest-first pagination만 제공한다.

### API-only write와 재시도·도배 제어

문제:

- anonymous Auth를 사용해도 browser가 table을 직접 쓰게 두면 Turnstile, rate limit과 입력 검증을 우회할 수 있다.
- 네트워크 재시도로 같은 글이 여러 번 생성되거나, 재시도가 rate quota를 중복 소모할 수 있다.
- JWT가 있더라도 request body의 `authorId`를 신뢰하면 다른 사용자를 가장할 수 있다.

선택:

- 모든 create·delete·report를 Vinext server route로만 받고, browser role의 table write와 security-definer RPC 실행은 database ACL로 차단한다.
- handler는 feature flag → JWT actor 검증 → Turnstile → trusted proxy IP의 daily HMAC → plain-text validation → service 순서로 fail-closed 처리한다.
- 게시글·댓글은 `(actor, idempotency_key)`로 기존 row를 먼저 확인하여 성공한 요청의 재시도는 추가 rate event를 소모하지 않는다.
- 새 write는 actor와 daily abuse key 둘 중 하나라도 제한에 닿으면 거부한다. 기본값은 게시글 3회/10분, 댓글 10회/10분, 신고 10회/1시간이다.
- 작성자는 JWT에서 검증한 actor ID로만 설정하고, 첫 write 시 HMAC 기반 nickname을 profile에 저장해 이후에도 유지한다.
- 삭제는 ownership을 확인한 뒤 `status=deleted`와 `deleted_at`을 함께 저장하는 soft delete로 처리한다.
- 신고 등록·중복 방지·10명 집계·임시 숨김은 하나의 database RPC transaction에서 수행한다.

결과와 한계:

- Local Supabase를 빈 database에서 reset한 후 schema lint와 pgTAP 14개로 browser write 거부, rate limit, 10명·긴급 숨김과 중복 신고 거부를 검증했다.
- Server는 외부 provider의 raw error를 response로 반환하지 않고 고정된 safe code와 한국어 메시지만 제공한다.
- IP header 신뢰 경계는 Cloudflare `CF-Connecting-IP`로 고정했으므로 비 Cloudflare 배포에서는 trusted proxy 정책을 별도로 재설계해야 한다.
- Server API 완료 후 browser의 anonymous session과 사용자 UI를 연결했다.

### Community UI의 정보 밀도와 익명 session UX

- 기존 market dashboard의 semantic color token·라이트/다크 테마를 유지하고 Community만의 새 palette는 추가하지 않았다.
- Feed는 제목·요약·작성자·시각·댓글 수로 구성하고, 외부 link는 preview를 scrape하지 않고 hostname만 표시한다.
- Form은 visible label과 글자 수, inline error를 제공하며 button과 navigation에 최소 44px 높이와 visible focus ring을 적용했다.
- 실패한 write의 idempotency key는 재시도에 재사용하고 성공 후에만 초기화한다.
- 기존 Supabase anonymous session이 있으면 재사용하고, 없을 때만 Turnstile token으로 새 익명 계정을 만든다. Provider 원문 오류는 UI에 노출하지 않는다.
- Browser data를 삭제하면 기존 작성물의 삭제 권한을 복구할 수 없다는 한계를 작성 폼에 항상 표시한다.
- Release gate 전에는 production navigation에서 Community를 숨기고 direct page에는 준비 상태만 표시한다.

### 관리자 OTP와 atomic moderation 경계

문제:

- 공개 익명 session과 운영자 session이 모두 Supabase Auth를 사용하므로 JWT가 있다는 사실만으로 관리 권한을 부여할 수 없다.
- 콘텐츠 상태 변경, 신고 해결과 감사 로그가 각각 실행되면 중간 실패 시 운영 기록과 사용자 화면이 서로 달라질 수 있다.
- 관리자 화면에서 신고자 신원이나 provider 오류를 그대로 보여 주면 moderation에 필요하지 않은 개인정보와 내부 정보가 노출된다.

선택:

- 운영자는 미리 만든 영구 Supabase 사용자로 email OTP 인증하고, server가 JWT를 다시 검증한 뒤 `community_admins` membership row를 확인한다. OTP 요청에는 `shouldCreateUser: false`를 적용해 관리 화면에서 계정이 자동 생성되지 않게 한다.
- 관리자 route는 public navigation에 연결하지 않고 Community feature flag가 꺼지면 인증보다 먼저 404를 반환한다. 요청 body의 관리자 ID는 무시하고 검증된 JWT 사용자 ID만 사용한다.
- 숨김·복원·삭제는 대상 상태 변경, 같은 대상의 open 신고 해결과 `community_moderation_actions` 감사 기록을 하나의 security-definer RPC transaction으로 처리한다.
- 사용자 제한은 종료 시각이 미래인지 검증해 sanction과 감사 기록을 함께 만들며, 게시글·댓글 write는 활성 sanction을 rate limit보다 먼저 확인한다.
- 신고 queue DTO는 신고 사유와 대상 문맥만 제공하고 `reporter_id`와 abuse key를 반환하지 않는다. 삭제와 사용자 제한은 UI에서 한 번 더 확인하고 성공·실패 결과를 명시한다.

결과와 한계:

- Local database reset, schema lint와 pgTAP으로 browser role의 moderation RPC 거부, non-admin 거부, atomic 신고 해결·감사 기록과 활성 제한 생성을 검증했다.
- API·component test로 401·403·400의 안전한 오류, 잘못된 cursor, OTP 자동 가입 차단, 신고자 비공개와 위험 조치 확인 단계를 검증했다.
- 초기 운영자 계정 생성과 `community_admins` row 등록은 Supabase Dashboard에서 수동으로 수행한다. 별도 bootstrap endpoint나 공개 admin 가입 경로는 제공하지 않는다.
- Email OTP template, 실제 권리침해 담당 연락처와 production 환경 확인은 release gate에서 다시 검증하며 그전에는 Community를 공개하지 않는다.

## 9. 예상 면접 질문과 답변

### 왜 실제 시세 대신 추정가를 만들었나요?

실시간 KRX 데이터는 단순 기술 문제가 아니라 정보이용 계약과 재배포 권리의 문제였다. 개인 증권사 API로 프로토타입은 만들 수 있었지만 광고형 공개 서비스로 확장하기 어려웠다. 그래서 공개 파생상품 데이터를 이용하되 실제 주가라고 주장하지 않고 24시간 시장 기대를 보여주는 제품으로 문제를 재정의했다.

### 추정가 알고리즘은 무엇인가요?

한국 주식을 참조하는 해외 파생상품 가격을 Bithumb KRW-USDT 합성환율로 원화 환산한다. 공급자와 환율의 최신성·단위·범위를 검증하고, 검증된 국내 종가가 확보되면 백테스트를 통과한 종목에 한해 기준점 보정을 적용한다.

### 왜 현재 환율을 과거 차트에 곱하지 않았나요?

그 방식은 과거의 환율 변화를 무시해 OHLC를 왜곡한다. 파생 1분 candle과 동일 시각의 환율 candle을 결합한 뒤 상위 봉으로 집계하는 순서를 선택했다.

### NXT와 KRX 가격이 다른데 어떤 값을 기준으로 하나요?

두 시장은 별도 주문장이므로 같은 시각에도 마지막 체결가가 다를 수 있다. 현재 Hyperliquid 상품이 KRX 주식을 참조하므로 정규장 대표 기준은 KRX로 두고, NXT는 프리·애프터 세션의 검증 기준으로 분리한다.

### 오차율을 어떻게 검증하나요?

동일 시각의 snapshot끼리 APE를 계산하고 세션별 MdAPE, P95, 방향 일치율을 집계한다. 지연 실제값을 현재 추정가와 비교하지 않는다. 최소 20거래일 뒤 1차 평가하고 60거래일 뒤 종목 확대를 결정한다.

### 1,000명이 접속하면 API 호출도 1,000배가 되나요?

아니다. 공급자별 cache와 in-flight 병합으로 서버가 하나의 snapshot을 만들고 방문자에게 fan-out한다. 호출량은 방문자 수가 아니라 cache 갱신 주기에 가깝게 유지된다.

### 로그인 없이 작성자를 어떻게 구분하나요?

Supabase anonymous Auth가 email·phone 없이 발급한 JWT의 user ID를 server에서 검증한다. 요청 body의 작성자 ID는 신뢰하지 않으며, browser가 table을 직접 수정하지 못하도록 grant와 RLS를 함께 제한한다. 사용자가 browser data를 삭제하면 기존 익명 계정 접근권을 잃는 한계는 명시한다.

### 왜 Supabase를 선택했고 언제 교체할 계획인가요?

혼자 만드는 익명 Community MVP에 필요한 PostgreSQL, anonymous Auth와 RLS를 한 환경에서 빠르게 검증할 수 있고, schema를 migration으로 Git에 남길 수 있어 선택했다. 다만 플랫폼이 보안·법적 준수·확장성을 자동으로 해결한다고 보지 않는다. Free plan backup과 quota를 별도로 관리하고, OIDC·enterprise SSO·복잡한 조직 권한 또는 비용·가용성 요구가 커지면 표준 PostgreSQL을 중심으로 database와 인증 계층을 분리·이전한다.

### Database row를 API에서 그대로 반환하지 않는 이유는 무엇인가요?

Schema에 새 내부 column이 추가될 때 자동으로 공개되는 mass assignment·over-fetching 문제를 막기 위해서다. Repository에서 column을 명시하고 read service가 공개 DTO를 다시 구성해 작성자 UUID, 신고자, abuse key와 moderation 상태가 응답에 들어갈 경로를 차단했다.

### IP를 저장하지 않고 신고 도배를 어떻게 줄이나요?

신뢰된 proxy header에서 선택한 IP를 server memory에서 정규화한 직후 UTC 날짜와 함께 HMAC-SHA-256으로 변환한다. DB에는 daily HMAC 결과만 최대 24시간 보관하고 원본 IP는 저장하지 않는다. 사용자 UUID와 daily key를 동시에 집계해 어느 한쪽만 바꾼 신고가 자동 숨김 기준을 채우지 못하게 한다.

### 공급자 하나가 장애를 일으키면 어떻게 되나요?

자산군별 요청을 병렬로 분리하고 공급자별 회로 차단을 사용한다. 해당 종목만 stale 또는 unavailable로 바꾸고 다른 시장 데이터는 계속 제공한다.

### 왜 데이터를 찾기 쉬운 웹사이트에서 크롤링하지 않았나요?

기술적으로 가능하더라도 재배포 권리, 이용약관, DOM 변경과 차단 위험 때문에 제품 기반으로 삼지 않았다. 공식 공개 API와 권리가 확인된 데이터만 사용한다는 원칙을 선택했다.

### 가장 어려웠던 점은 무엇인가요?

가격을 가져오는 코드보다 데이터의 의미를 정확히 모델링하는 일이 어려웠다. 실제 상품, 파생 추정가, 지연값, stale과 미제공을 같은 숫자 필드로만 다루면 UI가 사용자를 오도한다. 이를 타입, 문구, 기준 시각과 테스트로 일관되게 유지하는 데 집중했다.

### 아쉬운 점과 다음 단계는 무엇인가요?

정식 KRX·NXT 실제 시세 계약이 없어 추정가를 실제 가격으로 보장할 수 없다. 다음 단계는 세션별 오차 snapshot을 축적하고, 계약 가능한 공식 공급자가 확보되면 실제값을 별도 계층으로 추가하는 것이다.

## 10. 프로젝트에서 증명하는 역량

- 모호한 아이디어를 데이터 계약과 UI 정책으로 구체화하는 제품 기획
- 외부 API rate limit, stale, timeout과 부분 장애 처리
- 금융 데이터의 단위·기준 시각·비교 기준 모델링
- React·TypeScript 기반 반응형 대시보드와 접근성
- TDD, 회귀 테스트, GitFlow와 원자적 커밋
- 공개 배포에서 개인정보·API 자격증명·데이터 권리를 고려하는 운영 설계
- 시행착오와 의사결정을 문서로 남기는 기술 커뮤니케이션
