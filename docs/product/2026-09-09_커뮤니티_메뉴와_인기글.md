# 커뮤니티 메뉴와 인기글

## 결정 과정

네이버 카페처럼 전체글·공지사항·인기글을 구분해 탐색하고 싶다는 요청에서 시작했다. PC에서는 좌측 메뉴, 모바일에서는 본문 위 세 개의 탭으로 같은 목록을 재사용한다. 기존 날짜·필독·공지 강조와 조회·추천 표시를 유지한다.

처음 제안한 최근 7일·추천 1개 이상 기준은 채택하지 않았다. 사용자는 이용자 수에 따라 운영자가 기준을 계속 조정하기보다 실제 추천 수대로 자연스럽게 순위가 바뀌기를 원했다. 따라서 기간과 최소 추천 수 조건을 두지 않고 전체 기간 추천순을 확정했다. 복잡한 가중치·조회 수 합산·설정용 관리 화면은 추가하지 않는다.

## 확정 동작

| 메뉴 | 대상과 순서 | 주소 |
| --- | --- | --- |
| 전체글 | 공개 글, 필독 → 공지 → 일반 / 같은 종류는 최신순 | `/community` |
| 공지사항 | 공개 필독·공지, 필독 우선 / 같은 종류는 최신순 | `/community?feed=notices` |
| 인기글 | 공개 일반 글, 추천 수 내림차순 → 작성일 내림차순 → ID 내림차순 | `/community?feed=popular` |

인기글에는 추천 0개도 포함한다. 공지·필독·숨김·삭제 글은 포함하지 않는다. 추천이나 취소는 기존 저장 기능을 사용하며 메뉴 진입·새로고침·다음 페이지 조회 시 최신 DB 값을 읽는다. 실시간 push나 자동 폴링은 아니다. 데이터가 없는 메뉴에는 빈 목록 안내를 보여준다.

## 구현과 이유

- 화면 메뉴 정의는 `lib/community/feed.ts`, 메뉴·레이아웃은 `app/community/page.tsx`에서 관리한다. 기존 게시판 UI를 재사용하고 메뉴마다 컴포넌트를 초기화한다.
- API의 `feed`를 허용 목록으로 검증한다. 알 수 없는 API 값은 400이며, 화면 URL의 알 수 없는 값은 전체글로 표시한다.
- DB에서 필터·정렬·limit을 적용한다. 이미 내려받은 한 페이지를 프런트에서 재정렬하는 방식이 아니다. 기본 20개, 최대 30개이며 다음 페이지 존재 확인용 한 행을 추가 조회한다.
- 인기글 커서는 조회 당시 추천 수·원본 시각(마이크로초 보존)·ID·메뉴를 담는다. 정렬한 추천 수와 커서의 추천 수는 같은 SELECT 결과를 사용한다. 공지사항 커서도 메뉴를 구분해 다른 메뉴에 재사용하지 못하게 한다. 기존 전체글 커서는 호환한다.
- 훅은 요청 세대 번호로 이전 메뉴·새로고침 전의 늦은 응답을 무시한다. 더 보기의 연속 클릭은 동기 잠금으로 방지하고, 실패하면 기존 목록을 유지하며 재시도 안내를 표시한다. 중복 ID는 목록에 다시 추가하지 않는다.
- 공개 DTO와 기존 관리자 권한·추천 중복 방지·RLS는 유지한다. 새로운 DB migration, 환경변수, 원격 설정 변경은 필요하지 않다. 자동 파기 job도 변경하지 않았다.

## 의도한 한계와 확장 경계

추천 수는 변하므로 여러 페이지가 하나의 고정 스냅샷은 아니다. 다음 페이지를 읽기 전에 추천 수가 변해 글이 커서 앞쪽으로 이동하면 그 글은 새로고침 후 보일 수 있다. 중복 표시를 방지하지만 실시간으로 모든 페이지를 재배열하지는 않는다. 새로고침하면 첫 페이지부터 최신 순위를 다시 조회한다.

이번 변경은 서버에서 정렬·페이지 처리하도록 구성한 것이며 대규모 부하 검증을 의미하지 않는다. 데이터와 트래픽 증가 시 실행 계획을 측정한 뒤 공개 일반 글의 추천 수·작성일·ID 복합 인덱스 및 짧은 캐시를 검토한다. 인기글 선정 기준 자체를 바꿀 필요는 없다. 기존 댓글 수 조회의 대량 데이터 최적화도 별도 측정 대상이다.

대댓글·이모지와 관리자 전체 원격 운영 검증은 후속 작업이다. 이번 변경을 해당 기능까지 완료한 것으로 해석하지 않는다.

## 검증

- 신규 실패 테스트를 먼저 확인한 후 구현: DB 인기글 정렬/공지 필터, 메뉴 전달·검증, 추천 0개 커서 및 다른 메뉴 커서 차단, 늦은 더 보기 응답 배제, 더 보기 실패·재시도, URL 기반 현재 메뉴 표시.
- 전체 테스트 623 passed / 20 skipped. 기존 선택 실행 SQL 통합 테스트 등 skip 항목은 이 실행에서 수행하지 않았다.
- `pnpm exec tsc --noEmit`, `pnpm lint`, `pnpm build` 성공. 기존 vinext route classification 안내는 남아 있다.
- 로컬 서버가 연결된 실제 데이터에서 추천 0개 테스트 글이 인기글에 표시되고 공지사항은 빈 목록으로 표시되는 것을 확인했다. 다수 글의 추천순/커서 동작은 자동 테스트로 확인했다.
- 브라우저 PC 1280×900 라이트, 모바일 390×844 라이트·다크에서 메뉴 전환과 표시 확인. 새 게시글·공지·추천을 원격에 생성하는 검증은 하지 않았다.
- 별도 읽기 전용 코드 리뷰에서 수정이 필요한 P0–P2 이슈 없음. 커서의 가변 순위 한계는 위에 기록했다.

## 참고 자료와 적용 이유

확인일: 2026-09-09. 전문이나 타사 소스·디자인 에셋을 복제하지 않고 개념을 참고했다.

- 사용자 제공 네이버 카페 공지 목록 이미지·대화: 게시판 탐색 구조, 기존 필독/공지 강조를 유지하는 요구 근거.
- [PostgreSQL ORDER BY](https://www.postgresql.org/docs/current/queries-order.html): 여러 정렬 키의 우선순위와 동점 처리 근거.
- [PostgreSQL LIMIT/OFFSET](https://www.postgresql.org/docs/current/queries-limit.html): 제한 조회 시 고유한 정렬이 필요하다는 근거. ID를 마지막 정렬 키로 사용한다.
- [React useEffect — 데이터 조회](https://react.dev/reference/react/useEffect#fetching-data-with-effects): 정리 함수와 늦은 응답 차단 방식 참고. 프로젝트는 요청 세대 번호로 같은 문제를 처리한다.
- UI/UX Pro Max 스킬의 `navigation active state`·React `responsive navigation` 검색: 현재 메뉴 강조·공유 가능한 URL·의미 있는 nav/link를 적용. TDD 및 minjae-commit 스킬에 따라 검증과 README/CHANGELOG를 함께 관리했다.
- Supabase JavaScript order/limit 문서 주소도 조회했으나 조회 도구가 404를 반환해 확인 근거로 사용하지 않았다.
