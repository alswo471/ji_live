# 지투라이브 익명 커뮤니티 설계

- 작성일: 2026-09-03
- 상태: 설계 승인
- 대상: 공개용 지투라이브 1차 커뮤니티

## 1. 목적

지투라이브 사용자가 별도의 회원가입 없이 시장과 종목에 관한 의견을 나누도록 한다. 자유로운 의견 교환은 허용하되 개인정보 침해, 저작권 침해, 불법 투자자문, 시세조종성 선동과 도배에 대응할 수 있는 최소한의 운영 체계를 함께 제공한다.

이 설계는 법률 준수를 보증하는 문서가 아니다. 공개 운영 전 실제 서비스 구성과 최신 법령을 기준으로 개인정보 처리방침, 이용약관, 데이터·콘텐츠 이용권을 다시 검토하고 필요한 경우 국내 법률 전문가의 확인을 받는다.

## 2. 확정 범위

### 포함

- 가입 화면이 없는 Supabase 익명 인증
- 무작위 표시 닉네임
- 게시글 목록, 상세, 작성과 작성자 삭제
- 댓글 작성과 작성자 삭제
- 게시글·댓글 신고
- 관리자 숨김, 삭제, 복구와 작성 제한
- 텍스트와 외부 링크만 허용하는 게시물
- Cloudflare Turnstile, 작성 제한과 Row Level Security(RLS)
- 개인정보·저작권·권리침해 신고 창구
- 개인정보처리방침, 서비스 이용약관과 커뮤니티 운영정책

### 제외

- 이미지와 파일 업로드
- 실시간 채팅과 쪽지
- 사용자 간 거래
- 유료 기능, 유료 종목 추천과 리딩
- 게시글 실시간 구독
- 이메일·전화번호·소셜 계정 수집

## 3. 선택한 접근법

### 검토한 선택지

1. 원본 IP 저장: 제재는 쉽지만 개인정보 보관 위험이 커서 채택하지 않는다.
2. 브라우저 UUID만 사용: 단순하지만 브라우저 데이터를 삭제하면 도배와 신고 제한을 쉽게 우회할 수 있어 채택하지 않는다.
3. Supabase 익명 계정과 단기 보안 식별값 조합: 개인정보 수집을 줄이면서 소유권과 기본적인 오남용 방지 기능을 제공할 수 있어 채택한다.

Supabase 익명 사용자는 이메일이나 전화번호 없이 고유 사용자 ID와 JWT를 발급받는다. 익명 사용자도 `authenticated` 역할을 사용하므로 JWT의 `is_anonymous` 클레임과 RLS 정책을 함께 검사한다. Supabase가 권장하는 CAPTCHA와 요청 제한을 반드시 적용한다.

## 4. 시스템 경계

### 브라우저

- 최초 커뮤니티 접근 시 익명 세션을 발급받는다.
- 공개 목록과 상세 내용을 조회한다.
- 게시글·댓글·신고 요청에 JWT와 Turnstile 검증값을 전달한다.
- 익명 UUID는 화면과 공개 응답에 노출하지 않는다.
- 브라우저 데이터가 삭제되면 기존 익명 세션과 작성물 관리 권한을 복구할 수 없음을 작성 전에 안내한다.

### 애플리케이션 API

- JWT의 유효성과 익명 사용자 여부를 확인한다.
- Turnstile, 본문 길이, 링크 수, 금칙어와 작성 간격을 검사한다.
- 원본 IP 대신 비밀키로 생성한 단기 HMAC 식별값만 도배 방지에 사용한다.
- 게시글·댓글·신고의 작성·삭제는 모두 애플리케이션 API를 통해서만 처리한다.
- 요청 본문의 작성자 식별값은 사용하지 않고 검증된 JWT의 사용자 ID를 API가 강제로 기록한다.
- 모든 검증을 통과한 일반 사용자 작업, 관리자 작업과 자동 파기 작업에서만 서버 전용 키를 사용한다.

### Supabase

- 서울 리전의 PostgreSQL, Auth와 RLS를 사용한다.
- 시장 시세 수집·계산 시스템과 커뮤니티 데이터를 분리한다.
- 1차에는 Realtime을 사용하지 않고 페이지네이션과 명시적 새로고침을 사용한다.
- 공개 key를 사용한 테이블 직접 쓰기는 권한과 RLS에서 모두 차단한다.
- 서버 전용 키는 브라우저 번들, 저장소, 로그와 오류 응답에 포함하지 않는다.

## 5. 데이터 모델

| 테이블 | 역할 | 공개 범위 |
| --- | --- | --- |
| `community_profiles` | 익명 UUID에 연결된 표시 닉네임과 상태 | 닉네임만 공개 |
| `community_posts` | 제목, 본문, 링크, 상태와 작성 시각 | 공개 상태만 조회 |
| `community_comments` | 댓글, 상태와 작성 시각 | 공개 상태만 조회 |
| `community_reports` | 대상, 사유, 신고자와 처리 상태 | 신고자·관리자만 접근 |
| `community_sanctions` | 작성 제한 종류와 만료 시각 | 관리자만 접근 |
| `community_moderation_actions` | 숨김·삭제·복구 사유와 처리 이력 | 관리자만 접근 |
| `community_abuse_keys` | 단기 HMAC 식별값과 요청 횟수 | 서버만 접근 |

공개 API는 내부 사용자 UUID, 신고자, 제재 기록과 보안 식별값을 반환하지 않는다. 목록 조회에는 필요한 열만 선택하고 전체 레코드를 그대로 직렬화하지 않는다.

## 6. RLS 원칙

- 누구나 `visible` 상태의 게시글과 댓글만 읽을 수 있다.
- 공개 key와 익명 JWT를 사용한 게시글·댓글·신고 테이블의 직접 `INSERT`, `UPDATE`, `DELETE`는 전부 거부한다.
- 작성·삭제·신고는 JWT와 Turnstile을 검증한 애플리케이션 API만 수행한다.
- API는 검증된 사용자 ID로 소유권과 중복 신고를 확인하고 요청자가 전달한 작성자 ID를 신뢰하지 않는다.
- 신고자는 자신의 신고 접수 결과만 API 응답으로 확인할 수 있고 다른 신고 내역을 볼 수 없다.
- 숨김·삭제·복구·제재는 관리자 권한을 별도로 확인한 API만 수행할 수 있다.
- 서버 전용 키를 사용하는 코드는 일반 사용자 API, 관리자 API와 자동 파기 작업에 한정하고 각 경로에서 수행할 수 있는 작업을 명시적으로 제한한다.
- 정책은 허용 규칙을 추가하기 전에 거부 상태를 기본으로 작성하고 별도의 RLS 통합 테스트로 검증한다.

## 7. 콘텐츠 정책

### 허용

- 시장과 종목에 관한 개인 의견
- 출처 링크가 있는 정보 공유
- 사실과 의견을 구분한 전망과 토론

### 금지

- 불법정보, 음란물, 도박과 범죄 유도
- 타인의 실명, 연락처, 계좌 등 개인정보 노출
- 명예훼손, 모욕, 협박과 차별·혐오 표현
- 기사, 유료 리포트와 이미지 등의 무단 복제
- 수익 보장, 유료 리딩방, 리퍼럴과 불법 투자자문 광고
- 허위사실 유포, 시세조종과 매수 선동 목적의 반복 게시
- 피싱, 악성코드, 단축 URL과 출처를 숨기는 링크
- 동일 내용 도배와 커뮤니티 목적에 무관한 광고

작성 화면에는 개인 의견과 사실을 구분하고, 게시물이 투자 권유나 투자 판단의 근거가 될 수 없다는 안내를 표시한다. 면책 문구는 불법 행위나 허가받지 않은 데이터·콘텐츠 이용을 정당화하는 수단으로 사용하지 않는다.

## 8. 신고와 관리

- 동일 익명 사용자는 같은 대상에 한 번만 신고할 수 있다.
- 일반 신고는 서로 다른 유효 사용자 10명의 신고가 누적되면 임시 숨김 처리한다.
- 개인정보 노출 또는 명백한 불법 콘텐츠 신고는 신고 수와 관계없이 즉시 임시 숨김한다.
- 관리자는 신고 10건 미만이어도 정책 위반이 명백하면 수동으로 숨길 수 있다.
- Turnstile, 익명 계정 생성 제한과 단기 HMAC 식별값을 조합해 다중 계정 신고를 중복 집계하지 않는다.
- 관리자는 숨김 콘텐츠를 검토해 삭제 또는 복구하고 판단 사유를 기록한다.
- 신고 기능을 반복적으로 악용하면 신고 또는 작성 기능을 제한한다.
- 사이트 하단에 개인정보·저작권·권리침해 신고 연락처와 처리 절차를 공개한다.

## 9. 개인정보 최소화와 보유기간

### 처리 항목

- Supabase 익명 사용자 UUID
- 무작위 닉네임
- 게시글, 댓글, 신고 내용과 작성 시각
- 인증과 보안 과정에서 생성되는 접속기록
- 원본 IP로부터 생성되며 역산을 방지하는 단기 HMAC 식별값

실명, 생년월일, 주소, 이메일, 전화번호, 증권계좌, 보유자산, 정확한 위치정보와 광고 목적의 사용자 프로파일은 수집하지 않는다.

| 데이터 | 보유 기준 |
| --- | --- |
| 공개 게시글·댓글 | 작성자 삭제 또는 운영정책에 따른 삭제 전까지 |
| 삭제된 게시글·댓글 | 분쟁 대응을 위해 접근을 제한해 30일 보관 후 자동 파기 |
| 단기 HMAC 식별값 | 생성 후 최대 24시간 이내 자동 파기 |
| 신고·관리 처리 기록 | 사건 처리 종료 후 90일 이내 자동 파기 |
| 익명 인증 사용자 | 공개 작성물·진행 중 신고가 없고 마지막 활동 후 90일이 지난 계정을 자동 파기 |

법령상 보존이나 진행 중인 분쟁 대응이 필요한 경우에는 해당 건만 접근을 제한해 필요한 기간 동안 별도 보관하고 종료 후 파기한다. 실제 배포 전 각 보유기간과 파기 작업이 정책 문구, DB 작업과 일치하는지 통합 검증한다.

## 10. 처리방침과 국외 처리 출시 조건

개인정보를 처리하면 처리 목적, 항목, 보유기간, 파기 방법, 정보주체 권리 행사 방법과 개인정보 보호 연락처를 포함한 개인정보 처리방침을 공개한다. Supabase 사용과 관련된 처리위탁·국외 이전 사항은 서비스 개설 시점의 계약, DPA와 하위 처리업체 목록을 확인해 다음 항목을 정확히 기재한다.

- 이전 또는 처리되는 개인정보 항목
- 처리되는 국가, 시기와 방법
- 이전받는 법인의 명칭과 연락처
- 처리 목적과 보유·이용 기간
- 이전 거부 또는 권리 행사 방법과 그 효과

서울 리전 선택은 주 데이터 저장 위치를 정하는 설정이며, 그 자체가 모든 법적 준수를 보증하지 않는다. 실제 값이 확인되지 않았거나 정책과 구현이 다르면 공개 배포를 차단한다.

## 11. 오류와 오남용 대응

- 인증 실패: 작성 내용을 유지하고 재인증 안내를 제공한다.
- Turnstile 실패: 저장하지 않고 재시도 방법을 안내한다.
- 요청 제한 초과: HTTP 429와 재시도 가능 시각을 반환한다.
- Supabase 장애: 읽기 화면과 시장 대시보드는 가능한 범위에서 유지하고 쓰기는 실패로 명확히 표시한다.
- 중복 제출: 요청 식별자로 게시글·댓글 중복 생성을 방지한다.
- 외부 링크: `https` 링크만 허용하고 단축 URL과 위험 스킴을 거부한다.
- 비밀 노출: 서버 전용 키나 HMAC 비밀값이 클라이언트·로그·저장소에 발견되면 배포를 중단하고 폐기·재발급한다.

## 12. 검증 기준

### 기능

- 익명 사용자가 가입 화면 없이 글과 댓글을 작성할 수 있다.
- 본인 작성물만 삭제할 수 있다.
- 일반 신고는 유효 사용자 10명에서만 자동 숨김된다.
- 개인정보·명백한 불법 콘텐츠 신고는 즉시 임시 숨김된다.

### 보안

- 다른 사용자의 UUID를 전달해도 수정·삭제할 수 없다.
- 공개 Supabase endpoint를 직접 호출해 게시글·댓글·신고를 작성하거나 변경할 수 없다.
- 브라우저의 공개 키로 관리자 테이블을 읽거나 쓸 수 없다.
- 서비스 역할 키와 비밀값이 클라이언트 번들 및 Git 이력에 없다.
- 다중 계정, 반복 제출, 신고 도배와 링크 우회가 제한된다.

### 개인정보와 운영

- 처리방침의 수집 항목·보유기간·국외 처리 정보가 실제 설정과 일치한다.
- 24시간·30일·90일 파기 작업을 테스트 데이터로 검증한다.
- 권리침해 신고 접수부터 숨김, 검토, 삭제 또는 복구까지의 관리 흐름을 검증한다.
- 시세·뉴스·사용자 콘텐츠의 출처와 이용 범위를 분리해 기록한다.

### 품질

- 모바일과 데스크톱, 라이트·다크 모드에서 주요 흐름을 확인한다.
- 키보드 탐색, 포커스 표시, 오류 메시지와 색상 외 상태 표현을 확인한다.
- lint, 타입 검사, 테스트와 production build가 통과해야 한다.
