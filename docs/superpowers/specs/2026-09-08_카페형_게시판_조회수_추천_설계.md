# 카페형 게시판·조회수·추천 설계

## 승인과 목표

사용자는 네이버 카페를 참고한 게시판형 UI, 실제 조회수와 추천 구현을 승인했고 중간 승인 질문 없이 실행하도록 요청했다. 네이버의 색상·로고·소스를 복제하지 않고 제목 중심 표 형식과 익숙한 작성/목록 이동을 지투라이브의 기존 테마에 적용한다.

## 화면

- 목록: 제목·댓글 수, 작성자, 작성일, 조회수, 추천 수. 모바일은 제목 아래 메타정보를 묶는다. 최신순 cursor 페이지네이션은 유지한다. 검색·인기순·조회수 기반 정렬은 범위 밖이다.
- 작성: `/community/write` 별도 페이지. 기존 PostForm·익명 인증·Turnstile·validation을 재사용한다. 성공하면 생성된 글 상세로 이동한다. 취소/목록으로 이동은 링크로 제공한다. 페이지를 떠나면 초안이 사라짐을 명시한다.
- 상세: 제목·작성 정보·조회수, 본문, 추천 버튼과 수, 댓글·추가 로딩, 댓글 작성, 목록으로 돌아가기. 추천 상태는 aria-pressed로 전달하고 대기·실패 상태를 표시한다. 본인 글 추천은 비활성화한다.
- 실패한 집계를 0으로 꾸미지 않는다. 미연결/실패는 `—`와 안내로 표시한다. 기존 글의 집계 시작값 0은 신규 migration 적용 후 실제 0이다. 과거 조회수를 소급 추정하지 않는다.

## 서버·DB

브라우저 → 기존 인증 경계 → service-role 전용 RPC → PostgreSQL transaction. 클라이언트가 수량·actor ID를 정하지 못한다. JWT에서 검증한 actor만 사용한다. anon/authenticated 직접 쓰기와 RPC 호출을 허용하지 않는다.

조회는 같은 actor·post의 마지막으로 인정된 조회부터 정확히 24시간(rolling window)에 1회다. post 행 잠금과 `(post_id, actor_id)` unique 키로 동시 요청을 직렬화한다. 상세가 로드된 뒤 인증·사용자 확인이 가능한 경우 별도 POST로 집계한다. 세션이 없으면 기존 익명 인증을 준비하되 실패해도 글 읽기는 막지 않는다. 목록 미리 가져오기나 GET만으로 집계하지 않는다.

추천은 `(post_id,actor_id)` 1개이며 `recommended:true/false`라는 원하는 상태를 전송한다. toggle RPC는 재시도 때 반대로 바뀔 수 있으므로 쓰지 않는다. 동일 상태 재요청은 숫자를 바꾸지 않는다. 본인 글·숨김/삭제 글·제재 사용자는 거부한다. 취소 후 재추천을 허용한다.

서버의 기존 actor+daily HMAC rate limit을 재사용하되 action을 분리한다. 조회 60회/60초, 추천·취소 합계 20회/60초. 동시 갱신은 DB transaction에서 처리한다. 원본 IP를 저장하지 않는다. IP 기반 제한은 자정 UTC 또는 HMAC 교체 때 달라질 수 있으며, actor 기준 중복 방지는 유지한다. 브라우저 데이터 삭제·새 기기를 이용하는 중복을 완벽히 방지하는 기능은 아니다.

조회 receipt는 24시간 dedup에 필요한 actor·post·last_counted_at만 저장하고, 오래된 receipt는 스케줄러로 정리한다. 추천 관계는 취소 시 즉시 제거하고, auth 사용자 파기·게시글 실제 파기 시 cascade한다. 누적 조회 숫자는 receipt 파기 후에도 보존한다. 추천 수는 남아 있는 추천 관계와 일치하게 유지한다. 기존 콘텐츠 1년 보관·legal hold 정책은 변경하지 않는다.

## 배포와 검증

새 migration은 컬럼·전용 table·RPC 추가와 제한 action 확장으로 구성한다. 기존 migration을 수정하지 않는다. DB 먼저 적용한 뒤 앱을 반영한다. 원격 적용 전 로컬 PostgreSQL에서 중복·동시성·권한·정리 동작을 검증한다. 원격 연결 권한을 확보하지 못하면 앱에 가짜 수치를 넣지 않고 적용 대기 상태를 명확히 알린다. 원격 reset·전체 DB 교체·테스트 계정 무단 삭제는 하지 않는다.
