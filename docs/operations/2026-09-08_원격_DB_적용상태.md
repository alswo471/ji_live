# 커뮤니티 원격 DB 적용 상태

> 현재 상태 (2026-09-09): `202609090002`까지 원격 반영 완료. 추천수 503 해소와 실제 추천·취소 검증에 이어 [대댓글 DB 적용·조회·입력창 확인](./2026-09-09_대댓글_DB_적용체크리스트.md) 완료. 콘텐츠 자동 파기는 비활성. 아래 이전 확인 결과는 원인과 의사결정 이력으로 보존한다.

## 확인 결과

2026-09-08 서울 리전 Supabase 프로젝트는 `ACTIVE_HEALTHY`이며 CLI 연결과 schema 조회에 성공했다. 비밀번호·키·사용자 데이터는 출력하거나 이 문서에 저장하지 않았다.

- 원격 migration 이력: `202609030001`~`202609030003` 적용.
- 로컬에만 있는 기존 migration: `202609040001`, `202609040002`, `202609040003`, `202609070001`.
- 실제 원격 schema의 `consume_community_rate_limit` 반환형은 `boolean`이다. 최신 코드가 기대하는 JSON 응답과 달라, 이력만 빠진 상황으로 볼 수 없다.
- 조회수·추천 신규 migration은 아직 원격에 적용하지 않았다.

## 일괄 적용을 하지 않은 이유

기존 미적용 변경에는 관리자 복구 기능, 보관 정책 변경과 `community-retention-every-minute` 예약 작업이 포함된다. 새 조회수·추천 기능만 적용하는 것으로 안내한 뒤 기존 데이터 정리 작업까지 조용히 활성화하면 안 된다. `migration repair`로 이력만 맞추거나 원격 DB를 reset하지 않는다.

## 적용 순서

1. 최신 migration을 기존 데이터를 초기화하지 않는 로컬 DB에 적용하고 권한·집계·동시성·정리 테스트를 수행한다.
2. 원격 백업/복구 수단과 기존 데이터에 대한 보관 정책 적용 범위를 확인한다.
3. 관리자/보관 정책 미적용분과 예약 작업 활성화를 포함한다는 점을 명시하고 원격 적용 범위를 확정한다.
4. 확정된 migration만 순서대로 적용한다. 적용 후 RPC 반환형과 권한, 예약 작업 상태를 확인한다.
5. 앱 API 및 실제 화면을 재검증한다. 그 전에는 원격 연동 완료로 표현하지 않는다.

원격 프로젝트의 정상 상태와 애플리케이션 schema의 최신 상태는 별개다. 목록 조회 성공만으로 쓰기·추천·관리자 기능까지 정상이라고 판단하지 않는다.

## 2026-09-09 추천수 오류 재확인

사용자가 상세 화면의 `추천 수를 불러오지 못했습니다.` 오류 해결을 요청했다. systematic-debugging 절차에 따라 화면에 연결된 API와 원격 schema를 읽기 전용으로 재확인했다.

- `GET /api/community/posts/5414b06a-3238-43e7-a430-c55d1a0a3ec5/engagement`: HTTP **503**, code `community_engagement_unavailable`.
- 원격 migration 이력은 여전히 `202609030001`~`202609030003`이다.
- `community_posts.view_count`, `community_posts.recommendation_count`, `community_post_recommendations` 테이블은 실제로 존재하지 않는다.
- `consume_community_rate_limit`의 실제 반환형은 여전히 `boolean`이다.
- 현재 engagement-service의 조회는 위 집계 열을 요구하며, DB 오류를 안전한 503으로 변환한다. 따라서 화면의 CAPTCHA 성공 여부와 무관하게 집계를 읽을 수 없다.

원인은 최신 앱 코드와 원격 DB의 적용 버전 불일치다. 새로고침이나 오류 문구 변경, 임의의 0 표시로 해결하지 않는다. 실제 해결에는 선행 관리자·보관 정책·집계 및 공지 migration 적용과 이후 API 재검증이 필요하다. 선행 예약 작업은 보관기한이 지난 데이터의 실제 파기를 활성화하므로 적용 전 백업/복구 수단, 대상 범위와 예약 실행 승인을 확인한다. 이번 진단에서는 원격 변경·데이터 삭제를 수행하지 않았다.

## 2026-09-09 승인 후 실제 해결

사용자가 적용 의미를 확인한 뒤 진행을 승인했다. 추천수 해결과 자동 파기를 분리해 다음 순서로 처리했다.

1. 원격 `public` 및 `supabase_migrations`의 schema/data logical dump를 저장소 밖 비공개 디렉터리에 백업했다. 디렉터리 700, SQL 파일 600 권한이며 Git에 포함하지 않았다. 이 백업은 커뮤니티 변경 범위용이며 Auth·Storage 전체 재해복구 백업은 아니다.
2. 기존 게시글 1개·댓글 1개, migration 030001~030003, pg_cron 미설치, 실행 중 retention 없음, 만료된 신고 중복방지 HMAC 1개를 확인했다. 원문·키를 로그에 출력하지 않았다.
3. 기존 migration 파일을 바꾸지 않고 040001·040002·040003·070001·080001·090001 및 각 적용 이력을 한 transaction으로 구성했다. retention 잠금 및 대상 table 잠금 뒤 기존 row 전체를 임시 snapshot으로 보관하고 신규 열을 제외한 기존 값의 동일성을 transaction 안에서 검사했다. 신고 HMAC의 정책상 만료 제거만 별도로 허용했다.
4. 생성된 매분 retention job은 **commit 전에 비활성화**하고, 다른 활성 retention job이 없음을 검사했다. 초기 시험의 `cron.job` 직접 UPDATE는 Supabase 권한 제한으로 거부됐고 변경은 rollback됐다. 공식 `cron.alter_job(..., active := false)`로 바꿔 전체 적용·보존·권한 검사를 통과한 뒤 ROLLBACK 시험에 성공했다. 재조회로 초기 migration/pg_cron 미설치 상태가 유지됨을 확인했다.
5. 같은 절차로 실제 commit했다. SQL 실패 시 전체 rollback되지만 **성공적으로 commit된 이후의 복구는 별도 복원 작업**이 필요하다. 시험 rollback을 백업 복원 리허설이나 무조건적인 사후 복구 보장으로 표현하지 않는다.

### 결과

- 원격 migration: 030001, 030002, 030003, 040001, 040002, 040003, 070001, 080001, 090001 적용 완료 (각 접두 연월일은 `202609`).
- 게시글·댓글은 각각 1개로 유지. 기존 제목·본문·상태 해시 일치 및 transaction 내부 원본 필드 비교 통과. 신고·관리 로그 row도 유지했다.
- 24시간이 지난 신고 중복방지 HMAC **1개가 null로 제거**됐다. 신고 내용 삭제는 아니며 변경 전 값은 비공개 백업에 있다. 보존 정책에 반하므로 서비스에 임의로 복원하지 않는다.
- `community-retention-every-minute`: inactive. 글·댓글·계정 자동 파기를 이번 작업에서 실행하지 않았다.
- `community-view-receipts-hourly`: active. 만료된 조회 중복방지 receipt만 정리하며 누적 조회·추천은 유지한다.
- anon의 집계 RPC 직접 실행 불가, service_role의 RPC 실행 가능, service_role의 종류 열 직접 insert 불가 확인.
- 실제 앱 집계 GET **503→200**. 적용 직후 저장된 조회/추천은 0/0이었다. 브라우저 접근으로 조회 1이 반영됐고 새로고침 후에도 1로 유지됐다. 추천 버튼으로 **0→1→0** 저장/취소와 별도 GET 반영을 확인했다. 테스트 추천은 취소했다.
- 최초 화면의 일시적인 Turnstile 로딩 실패는 새로고침 후 자동 사용자 확인 성공으로 해소됐으며 인증 우회나 테스트 키 교체는 하지 않았다.

### 남은 배포 경계

- 매분 retention 활성화를 요구하는 release gate는 현재 의도적으로 충족하지 않는다. 공개 배포 승인과 자동 파기 검증 없이 이를 우회하거나 job을 재활성화하지 않는다.
- 추후 익명 계정 파기를 활성화할 때 해당 계정의 추천 관계 cascade 및 추천수 감소 영향도 검토한다.
- 이번 변경은 연결된 원격 DB 반영이다. Git push·develop 병합·Oracle 배포 또는 좌측 메뉴·인기글·대댓글·이모지 구현 완료를 뜻하지 않는다.
