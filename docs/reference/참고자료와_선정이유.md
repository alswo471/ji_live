# 참고자료와 선정 이유

기능·데이터 공급자·알고리즘·UI 정책을 결정할 때 확인한 외부 자료와 실제 적용 범위를 기록한다. 링크만 모으는 문서가 아니라, 나중에 같은 결정을 검토하거나 교체할 때 근거와 한계를 빠르게 찾기 위한 기록이다.

## 기록 원칙

기능 기획이나 구현 기준이 바뀔 때 아래 항목을 함께 갱신한다.

- 확인일과 공식 문서 URL
- 해결하려던 문제와 선택한 방식
- 문서에서 실제로 사용한 계약·단위·시간 기준
- 선택 이유와 검토한 대안
- 자료만으로 보장할 수 없어 사용하지 않은 값
- 영향을 받은 설계·코드·테스트
- 재검토가 필요한 조건과 현재 한계

블로그와 화면 관찰은 아이디어 탐색에만 사용할 수 있다. 데이터 계약, 거래 시간, 권리와 API 동작은 가능한 한 거래소·정부·공급자의 공식 문서로 검증한다.

## 2026-09-03 Community database와 공개 write 경계

### Supabase backend 선택 배경과 재검토 기준

- 확인일: 2026-09-03
- 공식 문서: [Architecture](https://supabase.com/docs/guides/getting-started/architecture), [Custom Claims & Role-based Access Control](https://supabase.com/docs/guides/api/custom-claims-and-role-based-access-control-rbac), [About billing](https://supabase.com/docs/guides/platform/billing-on-supabase), [Database Backups](https://supabase.com/docs/guides/platform/backups)
- 보조 참고자료: Logto의 [AI 스타트업이 Supabase를 선택하는 이유와 한계점](https://blog.logto.io/ko/supabase-ai-limitation)
- 해결하려던 문제: 혼자 개발하는 익명 Community MVP에서 PostgreSQL, 사용자 소유권, 접근 제어, migration과 초기 운영 환경을 각각 따로 구축하는 비용을 줄이되 추후 이전 가능성을 남긴다.
- 선택 이유: 관리형 PostgreSQL을 중심으로 Auth, PostgREST와 RLS를 함께 사용할 수 있고, 현재 필요한 anonymous session과 row 단위 권한을 schema·migration·test로 재현할 수 있다. Free plan은 제품 가설 검증 단계의 초기 비용을 낮춘다.
- 실제 적용 범위: Supabase는 Community Auth/Postgres를 담당한다. 공개 write는 Supabase browser direct write가 아니라 Vinext API의 JWT·Turnstile·rate limit 검증 뒤에만 허용하며, 시장 데이터 수집·cache와 Oracle application 배포는 별도 계층으로 유지한다.
- 자료 해석 주의: Logto 글은 빠른 개발과 비용, 향후 전문 인증 도입 필요성을 검토하는 업계 관점으로만 사용한다. Logto가 인증 제품을 제공하므로 비교 주장에는 이해관계가 있으며, 가격·quota와 기능 유무는 Supabase 공식 문서를 우선한다.
- 사용하지 않은 주장: Supabase에 custom claim·RBAC 구현 방법이 전혀 없다는 주장은 채택하지 않는다. 공식 문서는 Auth Hook, custom claim과 RLS를 이용한 RBAC 구현을 제공한다. 다만 조직·tenant·정책 관리가 제품 수준으로 모두 내장되어 있다는 뜻도 아니다.
- 현재 한계: Free plan에는 자동 backup이 없어 정기 `db dump`와 off-site 복구 검증이 필요하다. 익명 계정 abuse, SQL/RLS 정책 유지, database·egress·MAU·Realtime quota와 vendor-specific Auth/API 의존성도 application 운영 책임으로 남는다.
- 재검토 조건: 복잡한 조직·권한, OIDC provider, enterprise SSO, 여러 서비스의 통합 인증이 필요하거나 quota·비용·connection·가용성·RPO/RTO가 현재 plan을 넘으면 인증 전문 서비스, 다른 managed PostgreSQL 또는 self-hosting을 비교한다.
- 관련 기록: `docs/product/프로젝트_개발_히스토리.md`의 `Supabase를 Community backend로 선택한 이유`

### Supabase anonymous Auth와 abuse 방지

- 확인일: 2026-09-03
- 공식 문서: [Anonymous Sign-Ins](https://supabase.com/docs/guides/auth/auth-anonymous), [Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits), [CAPTCHA protection](https://supabase.com/docs/guides/auth/auth-captcha)
- 사용 범위: email·phone 입력 없는 익명 계정, JWT의 `is_anonymous` claim, Cloudflare Turnstile과 인증 endpoint 제한을 함께 적용하는 기준을 확인했다.
- 선택 이유: 회원가입 화면 없이 사용자별 작성물 소유권을 구분하면서 직접 입력하는 개인정보를 줄일 수 있다.
- 한계: 익명 사용자도 database에서는 `authenticated` role을 사용하며, browser data를 지우거나 기기를 바꾸면 기존 계정에 다시 접근할 수 없다. CAPTCHA만으로 다중 계정·도배가 없어지는 것은 아니므로 application rate limit과 daily HMAC abuse key를 함께 사용한다.
- 관련 구현: `supabase/config.toml`, `lib/community/config.ts`, 후속 anonymous session·Turnstile task

### Supabase email OTP와 관리자 계정 경계

- 확인일: 2026-09-03
- 공식 문서: [Passwordless email logins](https://supabase.com/docs/guides/auth/auth-email-passwordless)
- 사용 범위: 운영자에게 6자리 email OTP를 보내고 `verifyOtp`로 영구 session을 만드는 흐름, `shouldCreateUser: false`로 미등록 계정의 자동 가입을 막는 기준을 적용했다.
- 선택 이유: 공개 사용자의 anonymous Auth와 별개로 사이트 소유자만 접근하는 관리 화면을 비밀번호 저장 없이 운영하되, 실제 권한은 email 문자열이 아니라 server-side JWT 검증과 `community_admins` membership으로 결정한다.
- 사용하지 않은 주장: OTP 인증 성공 자체가 관리자 권한을 뜻하지 않는다. 공개 사용자는 admin 계정을 만들거나 membership을 추가할 수 없으며 초기 row는 운영자가 수동 등록한다.
- 한계: production에서는 email template에 `{{ .Token }}`이 포함됐는지, OTP 만료·재요청 제한과 SMTP 전달 상태를 release gate에서 다시 확인해야 한다.
- 관련 구현: `components/community/admin-login.tsx`, `lib/community/admin-auth.ts`, `app/api/admin/community/`

### Row Level Security와 API-only write

- 확인일: 2026-09-03
- 공식 문서: [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 사용 범위: exposed schema의 모든 table에서 RLS를 활성화하고, `anon`·`authenticated` grant와 row policy를 함께 제한해야 한다는 기준을 적용했다. Server secret은 `service_role`로 RLS를 우회하므로 browser에 전달하지 않는다.
- 선택 이유: 공개 browser에는 visible post·comment의 제한된 column read만 허용하고 모든 `INSERT`, `UPDATE`, `DELETE`를 Vinext API route 뒤로 격리한다.
- 한계: RLS 활성화만으로 기존 grant가 제거되지 않는다. migration과 실제 publishable key 거부 테스트를 release gate까지 함께 유지해야 한다.
- 관련 구현: `supabase/migrations/202609030001_community_schema.sql`, `tests/community/migration-contract.test.ts`

### Cloudflare Turnstile server-side validation

- 확인일: 2026-09-03
- 공식 문서: [Validate the token](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/), [Widget configurations](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/widget-configurations/)
- 사용 범위: browser token만 신뢰하지 않고 server가 `Siteverify` endpoint로 검증하며, token은 최대 2,048자·5분·1회 사용이라는 경계를 적용했다.
- 선택 이유: anonymous sign-in과 게시글 write 앞에서 자동화 요청 비용을 높이되 별도의 실명·전화번호 수집을 추가하지 않는다.
- 오류 정책: 빈 값·길이 초과·timeout·HTTP 실패·잘못된 JSON·`success !== true`를 모두 거부한다. Secret, token과 공급자 원문 오류는 사용자 응답이나 log에 포함하지 않는다.
- 한계: Turnstile은 하나의 abuse 방어 계층이지 사용자 신원 확인 수단이 아니다. JWT, application rate limit과 daily HMAC key를 함께 사용한다.
- 관련 구현: `lib/community/turnstile.ts`, `tests/community/turnstile.test.ts`

### Cloudflare Turnstile 자동화 test key

- 확인일: 2026-09-03
- 공식 문서: [Test your Turnstile implementation](https://developers.cloudflare.com/turnstile/troubleshooting/testing/)
- 사용 범위: local end-to-end test에서 공식 always-pass site/secret key와 `XXXX.DUMMY.TOKEN.XXXX`를 사용해 실제 Siteverify 요청 경계를 검증한다.
- 선택 이유: browser automation이 실제 challenge에서 불안정해지는 문제를 피하면서 production secret을 사용하거나 검증 함수를 fake로 교체하지 않는다.
- 제한: Dummy key는 local·test 전용이며 production 환경변수와 혼용하지 않는다. Generic CI의 외부 network 의존성을 피하기 위해 full integration은 local opt-in suite로 분리한다.
- 관련 구현: `tests/integration/community-security.test.ts`

### Local migration, region과 backup

- 확인일: 2026-09-03
- 공식 문서: [Local development workflow](https://supabase.com/docs/guides/local-development/cli-workflows), [Testing and linting](https://supabase.com/docs/guides/local-development/cli/testing-and-linting), [Available regions](https://supabase.com/docs/guides/platform/regions), [Database backups](https://supabase.com/docs/guides/platform/backups), [Supabase DPA](https://supabase.com/downloads/docs/Supabase%2BDPA%2B260317.pdf)
- 사용 범위: `config.toml`과 migration을 Git에 저장하고 `db reset`으로 빈 DB 재현, `db lint`로 PL/pgSQL 검사, production project의 Seoul `ap-northeast-2` 검증과 Free plan의 정기 off-site logical backup 필요성을 확인했다.
- 선택 이유: Dashboard에서 수동으로 만든 schema에 의존하지 않고 새 PC·검토 환경에서 같은 보안 정책을 재현한다.
- 사용하지 않은 주장: Seoul primary region 선택만으로 국내 개인정보 관련 법적 준수가 자동 보장된다고 기록하지 않는다. 처리위탁·국외 처리 내용은 공개 직전 최신 DPA와 subprocessor 정보를 다시 확인한다.
- 한계: Local stack은 TLS·운영 rate limit이 없는 개발 환경이므로 외부에 공개하지 않는다. Free plan은 자동 backup이 포함되지 않아 별도 `db dump`와 복구 검증이 필요하다.
- 관련 구현: `supabase/config.toml`, community migration, 후속 release gate·backup task

### 개인정보 고지와 Community 운영 release gate

- 확인일: 2026-09-03
- 공식 문서: [개인정보 보호법 제30조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1025127653), [개인정보 보호법 제28조의8](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334953), [개인정보보호위원회 개인정보 처리방침 작성지침(2026.4.)](https://www.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS217&mCode=D010030000.Updated&nttId=12018), [Supabase DPA (2026-03-12)](https://supabase.com/downloads/docs/Supabase%2BDPA%2B260317.pdf), [Supabase Database Backups](https://supabase.com/docs/guides/platform/backups), [Supabase Management API](https://supabase.com/docs/reference/api/getting-started)
- 사용 범위: 처리 목적·항목·근거·보유기간·파기·권리 행사·안전조치·처리위탁·국외 처리·연락처를 공개 정책의 필수 영역으로 두고 실제 운영 설정과 문서가 일치해야 한다는 release 기준을 적용했다.
- 선택 이유: 서울 primary region이나 서비스 제공자의 보안 인증만으로 운영자의 개인정보 보호 의무가 자동 충족되지 않으므로 code, database retention, 연락처와 최신 처리 사실을 함께 검증한다.
- Backup 적용: Supabase 공식 문서가 Free tier에 정기 `db dump`와 off-site backup을 권고하므로 주간 암호화 logical backup과 월간 격리 복구 시험을 운영 절차로 정했다.
- 사용하지 않은 주장: 면책 문구, Supabase 사용 또는 서울 region 선택이 무허가 데이터 재배포·저작권 침해·개인정보 관련 책임을 없앤다고 보지 않는다.
- 한계: 법령과 subprocessor는 바뀔 수 있고 실제 운영자 정보·연락처·계약 조건이 아직 확정되지 않았다. 따라서 현재 페이지는 운영 초안이며 release gate가 비활성 상태를 유지한다.
- 관련 구현: `lib/legal/community-policy.ts`, `app/legal/`, `scripts/check-community-release.mjs`, `scripts/backup-community-db.sh`, `supabase/migrations/202609030003_community_retention.sql`

## 참고했지만 계산 근거로 사용하지 않는 서비스

- [KoruLive](https://korulive.com/): 정규장 밖에서도 시장 기대를 이어서 보여주는 제품 방향과 자산 구성의 출발점으로 참고했다. 외부에서 관찰한 화면 값만으로 내부 데이터 공급자나 알고리즘을 단정하지 않는다.
- [Toss Securities 개발자센터](https://developers.tossinvest.com/docs/market-data#tag/market-data/getprices): 개인 프로토타입의 한국 주식 현재가와 보유종목 연동에 검토했다. 고정 IP, 호출 한도와 공개 재배포·상업 이용 조건을 해결하지 않은 상태에서는 공개 서비스 계산 입력으로 사용하지 않는다.
- [Naver Finance](https://finance.naver.com/): KRX·NXT 차이와 표시값을 수동 비교하는 참고 화면이다. 화면 크롤링 결과는 데이터 계약과 동일 시각 snapshot을 보장하지 않으므로 계산 입력으로 사용하지 않는다.
- [Kimpga](https://kimpga.com/): 보조지표, 캔들 차트 조작과 정보 밀도를 참고했다. 표시 데이터는 현재 프로젝트의 공식 공급자로 간주하지 않는다.
- [TradingView Chart Widget 문서](https://www.tradingview.com/widget-docs/widgets/charts/): 주기 전환, 시간축, 캔들·보조지표 경험을 참고했다. 현재 데이터 공급자나 계산 엔진으로 사용하지 않는다.
- [Polymarket](https://polymarket.com/): 24시간 시장 기대를 전달하는 제품 사례로 검토했지만, 한국 주식 추정가 계산 입력으로 채택하지 않았다.
- 증권사 화면과 실제 주문 화면: 같은 시각의 수동 검증에는 활용할 수 있지만 저장된 동일 시각 snapshot이 없으면 오차율 근거로 사용하지 않는다.
